 Step 13 (continued): Edit profile

 The Edit profile button on the profile page opens this screen. It changes the photo, name,
 username, bio, website and the private switch. The photo uploads only when the person
 taps Save, so cancelling never leaves a stray file in Storage. The username is checked on
 the device first, then for availability, and only when it actually changed.

 Two details matter. The update grant from Step 2 allows exactly these columns: username,
 display_name, bio, website, avatar_url and is_private. This screen therefore cannot touch
 counters or the verified badge, even if the code were changed. Also, no trigger accepts
 pending follow requests when an account turns public, so the screen accepts them itself
  in that case. Without that, those people would stay on Requested for good.

 Step 14: Follow, follow requests and follow lists

 The Follow button and its three states (Follow, Following, Requested) are already in the
  profile page from Step 13. This step builds the screens around them. The database does
 the bookkeeping. Following a public account is accepted at once. Following a private
 account creates a pending row, and the owner answers it. Accepting changes the row’s
  status, declining deletes the row, and the counters follow by trigger.

 Both lists and the request screen show people in the same way, so two small shared

 works differently. A hashtag is not a row in any table. It is an entry in the hashtags

 The topic function

 Open the SQL Editor in the Supabase dashboard, choose New query, and run this once. It
 counts only threads the caller is allowed to see. An empty query returns the most used
  topics, which the screen shows as Popular topics.

   -- Step 15: topic suggestions. Runs as the caller, so RLS still applies.
   create or replace function public.search_topics(q text)
   returns table (tag text, uses bigint)
   language sql stable security invoker set search_path = public as $$
     select h.tag as tag, count(*) as uses
     from public.threads t
     cross join lateral unnest(t.hashtags) as h(tag)
     where starts_with(h.tag, lower(regexp_replace(q, '[^A-Za-z0-9_]', '',
   'g')))
     group by h.tag
     order by uses desc, h.tag
     limit 20;
   $$;

 The design has three rules. First, opening the tab marks everything read, so the badge
  clears. Second, rows that were new when the tab opened keep a blue dot and a grey
 background until the person leaves the tab, so the person can still see what is new. Third,
 a notification that arrives while the tab is open is marked read at once, so the badge does
 not count something already on screen. For this the screen needs to know when its tab is
  selected, so the shell passes a flag.

 Step 17: Settings, block, mute, report and delete account

 Thread menus already let a person mute, block or report the author of a post (Step 10).
 This step adds the rest of the safety tools: the same actions on a profile, the lists where
 blocks and mutes are undone, and the Settings screen with log out and account deletion.

 The rules behind them are all in the database. Blocking removes any follow between the
 two people in both directions, and each side stops seeing the other’s threads. Unblocking
 does not bring the follows back. Muting only hides the person from your own feeds, and
 the other person is never told. Reports go into the reports table, and only you can read
 the ones you filed.

 Deleting an account is the one step the database cannot finish alone. The
  delete_my_account function from Step 2 removes the user, and the profile, threads, likes
 and follows go with it by cascade. Files in Storage are not part of that cascade, so the app
 deletes the person’s uploads first.
