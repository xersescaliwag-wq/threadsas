Threads Clone: Flutter, Supabase and adaptive_platform_ui Guide

 Build a Threads Clone with Flutter, Supabase
 and adaptive_platform_ui

 A step-by-step guide to a full Threads-style social app. The backend runs on Supabase
  (Postgres, Row Level Security, Storage and Realtime). The Flutter client uses
 adaptive_platform_ui and Cupertino widgets only, with no material.dart.

 How to use this guide

 Follow the steps in order. Each step names the file to create or the SQL to run, and every
 code block is meant to be copied as written. Later steps depend on earlier ones, so
 skipping ahead causes missing-file errors.

 Two rules apply to the whole project. First, your code never imports
  package:flutter/material.dart or any other Material library, and every screen is built from
 Cupertino widgets and adaptive_platform_ui. One limit applies: adaptive_platform_ui
 imports Material for its Android widgets and for drawer support, so Material code is
 compiled into every build, including iOS. That code belongs to the package, and this
 project cannot remove it while the package is in use. On iOS, most controls are Cupertino
 or native iOS views. Second, every table in Supabase has Row Level Security (RLS) turned
  on, with explicit policies. The publishable key is designed to ship inside client apps, so
 your data is protected by those policies rather than by keeping the key secret.

 This guide is delivered in parts. The document starts with the overview and the Supabase
 project settings. The database schema, the Flutter code and the screens are added in the
 sections that follow.

 Architecture at a glance

 The Flutter app talks to Supabase directly, so you do not need to run your own server.
 Supabase Auth signs each user in and issues a signed token (a JWT). The
 supabase_flutter client sends that token with every request. PostgREST turns table
 queries into SQL, and Postgres checks the RLS policies before returning any row. Triggers
 keep counters and notifications correct, Storage holds photos and videos, and Realtime
 pushes row changes to screens that subscribe to them.

   Flutter app (Cupertino widgets and adaptive_platform_ui only)
     Screens -> Riverpod providers -> Repositories -> supabase_flutter

     Storage ..... photos, videos and avatars in per-user folders
     Realtime .... pushes row changes (replies, likes, notifications)
     Postgres .... tables, RLS policies, triggers and functions

 Step 1: Configure the Supabase project

 Open your project in the Supabase dashboard and check these settings.

 Authentication, then Providers: keep Email enabled. While you develop, you can turn off
 Confirm email so new accounts sign in immediately. Turn it back on before launch,
 because the app handles both cases.

 Authentication, then URL Configuration: set the Site URL to http://localhost:3000 for now.
 Mobile deep links are needed only if you later add OAuth or magic links, and Step 21
 covers that.

 Database: nothing to change in the dashboard. Step 2 creates every table, function, policy
 and storage bucket from one SQL file. That file is delivered in three parts, so each part is
 easy to read and copy.

 Step 2: Create the database

 Open the Supabase dashboard, go to SQL Editor and choose New query. Run the three
 parts of this step in order on a new project, and run each part once. If you need to start
  again, create a new project instead of re-running the parts on top of existing data.

 Part A: tables and indexes

 Each table stores one kind of record. Threads live in a single table. A top-level post has no
 parent, a reply points to the thread it answers through parent_id, and a quote points to
 the thread it quotes through quote_id. Counters such as like_count are stored on the row
  itself, so feeds load quickly without counting rows on every request.

  Part B adds the triggers that keep counters, notifications and hashtags correct.

 Part B: business logic

 The triggers and functions in this part run automatically whenever data changes, so the
 app never has to keep counters, notifications or hashtags up to date by hand. Functions
 marked security definer run with the database owner's rights. That lets them update
 counters that ordinary users are not allowed to change directly. Each trigger is dropped
 before it is created, which keeps the script safe to run again.

 C: security, storage, realtime and functions

 Row Level Security is the security layer of the whole project. Once it is switched on, a
 table returns no rows unless a policy allows them. The policies below state exactly who
 can see and change each record, so the Flutter app never has to filter data for security
 reasons. Column grants add a second layer: they stop a user from changing protected
 columns such as follower counts or the verified flag, even through their own profile.

   // lib/core/errors.dart
   import 'package:supabase_flutter/supabase_flutter.dart';

   /// Turns Supabase errors into a sentence a person can read.
   String friendlyError(Object error) {
     if (error is AuthException) {
       if (error.message.toLowerCase().contains('invalid login credentials')) {
         return 'Wrong email or password.';
       }
       if (error.message.toLowerCase().contains('already registered')) {
         return 'An account with this email already exists.';
       }
       return error.message;
     }
     if (error is PostgrestException) {
       if (error.code == '23505') {
         return error.message.contains('username')
             ? 'That username is already taken.'
             : 'That already exists.';
       }
       // Messages raised by our triggers (for example, reply limits) are shown
   as they are.
       if (error.message.contains('row-level security')) {
         return 'You do not have permission to do that.';
       }
       return error.message;
     }
     if (error is StorageException) return error.message;
     return 'Something went wrong. Please try again.';
   }

 How actions refresh data

 After a write, refresh the smallest set of providers that the change touches. A like
 replaces one post in the feed with replacePost. A new reply invalidates
 threadDetailProvider for that conversation. A follow invalidates followStateProvider for
 that user and the following feed. Narrow refreshes keep the app quick on slow
 connections.

 Realtime needs an active connection. supabase_flutter disconnects the socket when the
 app goes to the background and reconnects on resume, so live updates pause and then
 catch up.

 Step 11: Compose: text, media, polls, reply controls and ghost posts

 The composer is one screen with four modes. A new thread starts empty. A reply shows
 the post it answers. A quote shows the post being quoted. An edit loads the existing text
 and settings, and only those can change, because media and polls are fixed once posted.
 The screen closes with the saved post, so the caller can add it to its list.

 The composer uploads media first, then creates the thread, and then creates the poll. If
 the poll fails, the thread is deleted, so no half-made post stays in the database (see
 ThreadRepository.createThread in Step 5).

 The limits come from lib/core/config.dart: 500 characters, 10 media files, and 2 to 4 poll
 options of up to 60 characters each. The database enforces the same limits, so a request
 that breaks them fails even if the app is changed.

 Step 12: Thread detail, nested replies and live updates

 Opening a post shows three things: the posts above it, the post itself, and every reply
 under it at any depth. The replies are shown as a tree. Each reply sits one step to the right
 of the reply it answers, up to four steps deep, so a long conversation stays readable on a
 phone.

 The page listens to Supabase Realtime. When someone replies, likes the post, or reposts
  it, the page reloads by itself. The realtime providers from Step 6 send the signal, and the
 screen reloads the thread through the detail provider.

 A quick reply box sits at the bottom. It replies to the post on screen. To reply to a single
  reply, the person taps that reply's reply button, which opens the composer with the right
 parent.

 Cards keep local copies of the posts they change, for example after a like or a vote. The
 page holds those copies in a small map until the next reload, so a card never flashes back
 to an older value.

 Step 11: Compose: text, photos, videos, polls, reply controls and
 ghost posts

 The composer is one screen with four jobs. It opens from the Post tab, from the reply
 button, from the quote choice in the repost sheet, and from Edit in the menu. Each job
 returns the saved post, so the card that opened it can update without a reload.


  Mode     How it opens                 What it writes

  New       The Post tab               A row in threads, with photos or videos, a
   thread                                               poll and an expiry time if chosen

   Reply      The reply button on a card or in a  A row in threads with parent_id set. The
               thread                         database links it to the conversation root

   Quote      Quote in the repost sheet      A row in threads with quote_id set. The
                                            quoted post appears inside it

   Edit         Edit in the menu                Only content, reply control and the hide-
                                                    like-count setting


 The screen enforces these rules. The database checks the same rules, so a bad request is
 refused even if the app is changed.

   Up to 500 characters. The field stops at 500, and the counter shows the count.
   A post needs text or at least one photo or video.
   Up to 10 photos or videos. Each one uploads to the thread-media bucket, inside a folder
   named with your user id, before the post is saved. If an upload fails, nothing is posted.
   A poll has 2 to 4 options. Each option needs text, and no two options may match. The
     poll runs for 1, 3 or 7 days. Polls belong to new threads and quotes, not replies.
   A ghost post disappears after 24 hours. The threads_select policy from Step 2 hides it
    from everyone once its time has passed, and the optional cron job removes the row
     later.

 The reply control has three choices: everyone, profiles you follow, or profiles you mention.
 The database checks the setting on the root thread, so it covers the whole conversation.
 For that reason replies do not show the control.

 A new thread refreshes the For you and Following feeds, and the author's Threads tab on
 the profile. A reply refreshes the thread page it belongs to, and the card's reply count
